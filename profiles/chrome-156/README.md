# chrome_156 profile

Evidence for the `chrome_156` profile, which is active in the table. Everything
here is regenerated by the commands below; none of it was hand-written.

## Files

| File | What it is |
| --- | --- |
| `captures.json` | 6 independent Chrome 156 connections to `tls.peet.ws/api/all`, with `pre_shared_key` removed (see below) |
| `captures.server-observed.json` | the raw capture exactly as received, including `pre_shared_key` on all six connections |
| `validation.json` | wire gate result, produced by `tools/verify-wire-capture.py` |
| `source-evidence.json` | the 12 audited source files at the 156 release tag, produced by `tools/collect-profile-evidence.py` |
| `trust-anchor-ids.json` | the 28 trust anchor IDs the captures advertise, in wire order |

Reproduce:

```sh
tools/verify-wire-capture.py --profile chrome_156 \
  --captures profiles/chrome-156/captures.json \
  --out profiles/chrome-156/validation.json

tools/collect-profile-evidence.py --version 156.0.8078.31 \
  --out profiles/chrome-156/source-evidence.json
```

## The capture had no full handshake

All six connections in the supplied capture carry `pre_shared_key (41)`; there
is **no** full-handshake sample. chrome_155 had one (its connection 0), which is
what made its extension set directly comparable.

Because of that, `captures.json` is the raw capture with `pre_shared_key`
removed from every connection, so the file describes the full-handshake
ClientHello shape that the profile table stores. Nothing else was touched: no
extension was reordered, no value rewritten. The untouched capture is kept
beside it in `captures.server-observed.json` so the edit is auditable.

That removal is not a guess about what Chrome would send. Verified before
editing: with `pre_shared_key` excluded, all six 156 connections agree on the
same 18-name extension set, and that set is **identical** to chrome_155's full
handshake — no extension added, none dropped. The only per-extension content
differences are the GREASE code points, which are random per connection by
design and are exactly what the project forbids pinning.

## Wire gate

`wire_verified: true`. 6 connections from 6 distinct source ports.

Byte-identical on every connection: de-GREASEd cipher list, supported groups,
signature algorithms, HTTP/2 fingerprint, trust_anchors payload, User-Agent.

Different on every connection (6 distinct values each, 3 required): client
random, session id, extension order, GREASE values, key share, ECH payload.

## What differs from chrome_155: the version, not the fingerprint

Every stable value the wire gate checks is identical to the chrome_155 capture:
the de-GREASEd cipher, group and signature lists, the extension set, the HTTP/2
fingerprint (`1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`), and the
`trust_anchors` payload (186 bytes of wire contents, 28 IDs). The only wire
difference is the User-Agent major, `155.0.0.0` -> `156.0.0.0`.

`tools/build-profile-entry.py` re-derives the cipher/group/signature/extension
values from these captures and **fails** if they disagree with the inherited
template before it writes an entry, so the reuse above is checked, not assumed.

The five network parameter groups (`tls`, `http2`, `http3`, `alpn`,
`websocket`) in the generated entry are byte-for-byte equal to chrome_155's.
What does differ, correctly, is the evidence block: the BoringSSL revision, the
`features.cc` size, and every audited line number.

## Not asserted: branch stability across patch releases

chrome_155 compared the first and last 155 stable release to show the audited
files do not move within a branch. Only one 156 build (`156.0.8078.31`) was
available here, so that comparison is **not** made for 156 and
`patch_release_comparison.identical_across_patch_releases` is `null` rather than
claiming a result that was never measured.
