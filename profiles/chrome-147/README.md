# chrome_147 profile

Evidence for the `chrome_147` profile, which is active in the table. Everything
here is regenerated by the commands below; none of it was hand-written.

## Files

| File | What it is |
| --- | --- |
| `captures.json` | 3 independent Chrome 147 connections |
| `validation.json` | wire gate result, produced by `tools/verify-wire-capture.py` |
| `source-evidence.json` | the 12 audited source files at the 147 release tag, produced by `tools/collect-profile-evidence.py` |

Reproduce the gate:

```sh
tools/verify-wire-capture.py --profile chrome_147 \
  --captures profiles/chrome-147/captures.json \
  --out profiles/chrome-147/validation.json

tools/collect-profile-evidence.py --version 147.0.7727.137 \
  --out profiles/chrome-147/source-evidence.json
```

## Wire gate

`wire_verified: true`.
3 connections from 3 distinct source ports.

Byte-identical on every connection: de-GREASEd cipher list, supported groups,
signature algorithms, HTTP/2 fingerprint and User-Agent. Different on every
connection: client random, session id, extension order, GREASE values, key share
and ECH payload.

The HTTP/2 fingerprint is
`1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`,
matching the 152--155 captures. The `trust_anchors` extension is absent, which is
correct for this release: `kTLSTrustAnchorIDs` is `FEATURE_DISABLED_BY_DEFAULT`
until 152.

## Provenance

Migrated from the pre-migration tree, where this release was audited by the
original browserleaks pipeline rather than by `tools/verify-wire-capture.py`.
Two capture directories exist there and they are not interchangeable:

* `chrome-147-release-validation/` is the peet.ws schema this repository's gate
  reads, but it was captured through a local forwarding proxy (`ip` is
  `127.0.0.1:<port>`), so every connection presents the same client address to
  the server and the capture cannot show connection independence.
* `chrome-147-browserleaks-boundary-20260822/` was captured on a real interface
  with `independent_processes: true`. Its `session-N.pcap` files are the primary
  evidence, and each holds a complete TLS connection.

`tools/migrate-browserleaks-captures.py` produced `captures.json` from that
second directory. BrowserLeaks reports only the *length* of each key share, so
the key material was read out of the matching ClientHello in the pcap — the same
source the original pipeline used — and each record was paired with its pcap by
searching for its TLS `random`, never by filename. The remap to the peet.ws
field names moves names only; no value is invented.

```sh
tools/migrate-browserleaks-captures.py --major 147 \
  --source new/captures/chrome-147-browserleaks-boundary-20260822 \
  --out profiles/chrome-147/captures.json
```
