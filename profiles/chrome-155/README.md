# chrome_155 profile

Evidence for the `chrome_155` profile, which is active in the table. Everything
here is regenerated by the commands below; none of it was hand-written.

## Files

| File | What it is |
| --- | --- |
| `captures.json` | 5 independent Chrome 155 connections to `tls.peet.ws/api/all` |
| `validation.json` | wire gate result, produced by `tools/verify-wire-capture.py` |
| `source-evidence.json` | the 12 audited source files at the 155 release tags, produced by `tools/collect-profile-evidence.py` |
| `trust-anchor-ids.json` | the 28 trust anchor IDs the captures advertise, in wire order |

Reproduce both:

```sh
tools/verify-wire-capture.py --profile chrome_155 \
  --captures profiles/chrome-155/captures.json \
  --out profiles/chrome-155/validation.json

tools/collect-profile-evidence.py --version 155.0.8059.12 --version 155.0.8059.40 \
  --out profiles/chrome-155/source-evidence.json
```

Chrome's reduced User-Agent reports `155.0.0.0`, so the captures cannot be
attributed to a patch build. Instead all twelve audited files were compared
between the first (`155.0.8059.12`) and last (`155.0.8059.40`) 155 stable
releases: **all twelve are identical**, so the audited surface is branch-stable
and the exact build does not change the fingerprint.

## Wire gate

`wire_verified: true`. 5 connections from 5 distinct source ports.

Byte-identical on every connection: de-GREASEd cipher list, supported groups,
signature algorithms, HTTP/2 fingerprint, trust_anchors payload, User-Agent.

Different on every connection (5 distinct values each, 3 required): client
random, session id, extension order, GREASE values, key share, ECH payload.

As in 152–154, the extension set differs by exactly `pre_shared_key (41)` on the
connections that resumed a session, which `verify-wire-capture.py` treats
separately.

## What differs from chrome_154: the version, not the fingerprint

Every stable value the wire gate checks is identical to the chrome_153 and
chrome_154 captures: the de-GREASEd cipher, group and signature lists, the
extension set, the HTTP/2 fingerprint
(`1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`), and the `trust_anchors`
payload (186 bytes of wire contents / 184 bytes of encoded list, 28 IDs). The
only wire difference is the User-Agent major, `154.0.0.0` → `155.0.0.0`;
`core/source/minicronet.cc` already emits `<major>.0.0.0` for any major above
104, so no code change is needed.

That reuse is not assumed: `tools/build-profile-entry.py` re-derives the
cipher/group/signature/extension values from these captures and **fails** if they
disagree with the inherited template before it writes an entry.

The trust_anchors payload carries the **same 28-ID set** as 153 and 154 in a
**different order**, which is a property of the process's `absl::flat_hash_set`
instance rather than of the release (see `profiles/chrome-152/README.md`). The
155 entry stores its own observed order; 154 and 155 happened to observe the same
permutation in their captures, so the generated table shares one array between
them.

## Source-level support for "nothing moved"

`net/base/features.cc` at 155.0.8059.40 keeps every network feature the table
reads at its 153/154 value: `kAlpsForHttp2` (line 32)
`FEATURE_ENABLED_BY_DEFAULT`, `kTryQuicByDefault` (904)
`FEATURE_ENABLED_BY_DEFAULT`, `kTLSTrustAnchorIDs` (749) and
`kNonMtcTrustAnchorIDs` (751) enabled, `kTlsGreaseSigalgs` (1039) enabled,
`kEnableTLS13EarlyData` (188) disabled.

Two upstream removals touch code this repository patches, and neither moves a
profile value:

- `kAvoidH2Reprioritization` (`features.cc:37` at 154,
  `FEATURE_DISABLED_BY_DEFAULT`) is **gone at 155**, and with it the
  `net/spdy/spdy_session.cc` early-return that read it. The profile-owned
  `avoid_h2_reprioritization` session parameter defaults to `false` and every
  pinned profile leaves it there, so the restored member-gated early return
  behaves exactly as the removed feature-gated one did (the feature was disabled
  by default in every release that had it).
- `net::SSLContextConfig::ech_enabled` is **gone at 155**; ECH policy is
  expressed solely through `SSLConfigService::GetEchMode()`, which the Core
  already implements per profile.

`net/spdy/spdy_session.cc` itself changed between 154 and 155 as a result of the
first removal, so it is no longer byte-identical to the 153/154 copy; the
audited `http2` signals the table stores are unaffected.
