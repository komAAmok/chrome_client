# chrome_153 profile

Evidence for the `chrome_153` profile, which is active in the table. Everything
here is regenerated by the commands below; none of it was hand-written.

## Files

| File | What it is |
| --- | --- |
| `captures.json` | 5 independent Chrome 153 connections to `tls.peet.ws/api/all` |
| `validation.json` | wire gate result, produced by `tools/verify-wire-capture.py` |
| `source-evidence.json` | the 12 audited source files at the 153 release tags, produced by `tools/collect-profile-evidence.py` |
| `trust-anchor-ids.json` | the 28 trust anchor IDs the captures advertise, in wire order |

Reproduce both:

```sh
tools/verify-wire-capture.py --profile chrome_153 \
  --captures profiles/chrome-153/captures.json \
  --out profiles/chrome-153/validation.json

tools/collect-profile-evidence.py --version 153.0.8010.12 --version 153.0.8010.37 \
  --out profiles/chrome-153/source-evidence.json
```

Chrome's reduced User-Agent reports `153.0.0.0`, so the captures cannot be
attributed to a patch build. Instead all twelve audited files were compared
between the first (`153.0.8010.12`) and last (`153.0.8010.37`) stable releases
of the branch: **all twelve are identical**, so the audited surface is
branch-stable and the exact build does not change the fingerprint.

## Wire gate

`wire_verified: true`. 5 connections from 5 distinct source ports.

Byte-identical on every connection: de-GREASEd cipher list, supported groups,
signature algorithms, HTTP/2 fingerprint, trust_anchors payload, User-Agent.
Different on every connection (5 distinct values each, 3 required): client
random, session id, extension order, GREASE values, key share, ECH payload.

As in 152, the extension set differs by exactly `pre_shared_key (41)` on the
connections that resumed a session, which `verify-wire-capture.py` treats
separately.

## What differs from chrome_152: the version, not the fingerprint

JA4 (`t13d1517h2_8daaf6152771_cb7bf5808d99`), the peetprint hash
(`fc97c1cdfb1409c9a9326c1b726d1dee`) and the Akamai HTTP/2 fingerprint
(`1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`) are byte-identical to the
chrome_152 captures. So are the de-GREASEd cipher, group and signature lists
and the extension set. The only wire difference is the User-Agent major,
`152.0.0.0` → `153.0.0.0`; `core/source/minicronet.cc` already emits
`<major>.0.0.0` for any major above 104, so no code change is needed. The
profile exists to pin the version so `chrome_153` impersonation reports the
right UA while reusing 152's wire parameters verbatim.

The trust_anchors payload carries the **same 28-ID set** as 152 in a **different
order**. That is expected and not profile-relevant: the order is a property of
the process's `absl::flat_hash_set` instance (see `profiles/chrome-152/README.md`
for the mechanism), so the 153 entry stores its own observed order and the Core
still inserts the set and lets absl order it. Both entries share one set;
`tools/inspect-client-hello.py` demonstrates the Core reproduces per-instance
ordering rather than a frozen permutation.

Source-level support for "nothing moved": five of the twelve audited files do
differ between the 152 and 153 tags (`boringssl_extensions`, `features`,
`http3`, `quiche_h3`, `tls`), but none of the differences moves a value the
table stores. In `features.cc` at `153.0.8010.37`: `kAlpsForHttp2` (line 32) and
`kTryQuicByDefault` (line 869) stay `FEATURE_ENABLED_BY_DEFAULT`,
`kTLSTrustAnchorIDs` (714) / `kNonMtcTrustAnchorIDs` (716) stay enabled,
`kTlsGreaseSigalgs` (1004) stays enabled, `kEnableTLS13EarlyData` (182) stays
disabled. `net/spdy/spdy_session.cc` — the entire HTTP/2 stack the table
configures — is byte-identical between `152.0.7977.83` and `153.0.8010.37`
(sha256 `666cf33958bc3ae1364dc0c71291d13e152422b85ad9b15d138c6094985c15be`), and
`client_socket_pool_manager.cc` still defines
`g_allow_size_randomization_for_proxy = true` unconditionally, so the proxy
pool-limit behaviour is unchanged from 152.
