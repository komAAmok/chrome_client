# profiles/

Runtime profile data and the evidence behind it. These are three different kinds
of artifact with three different lifetimes, which is why they are not merged into
one file.

## Runtime inputs (read by `tools/generate-profile-table.py`)

| File | Size | What it is | Regenerated by |
| --- | --- | --- | --- |
| `normalized_profiles.json` | 3.4 MB | The 55 profiles (`chrome_99`–`chrome_153`) the Core compiles into its read-only table: TLS, ALPN, HTTP/2 SETTINGS, HTTP/3, WebSocket and FeatureList parameters, each with its source evidence and digest. | Not in this repository — see the gap below. |
| `effective_protocol_params.json` | 44 KB | The effective protocol parameters per profile, flattened out of the above. | Same. |
| `network_feature_snapshots.json` | 0.7 KB | The frozen Chromium feature-default snapshot the table is checked against. | Same. |

These three are the generator's inputs and are consumed by exactly one tool
(`tools/generate-profile-table.py`), which emits
`core/source/minicronet/profile_table_generated.h`. That header is committed and
its regeneration is verified byte-for-byte in CI.

## Per-release evidence (not read at runtime)

`chrome-152/` and `chrome-153/` hold the capture evidence for those two
releases: `captures.json` (wire captures), `source-evidence.json` (the audited
Chromium source lines), `trust-anchor-ids.json`, `validation.json` and a
`README.md` with the reproduction commands.

Only the two newest releases have a directory. The earlier 53 profiles carry
their evidence inline in `normalized_profiles.json`, because that is where the
generator reads it from. The directories exist for the releases that were audited
by wire capture as well as by source.

## Known gap

`normalized_profiles.json` records `"generated_by": "tools/build-normalized-profiles.py"`,
and that tool is not in this repository. The runtime table therefore cannot be
rebuilt from a clean checkout; only its *consumers* are gated. Rebuilding it needs
the profile evidence pipeline that produced the captures. Until that tool is
migrated, treat these three files as inputs to be verified, not regenerated.

## Why not merge into one file

The three runtime files have different schemas and are read separately; merging
them would not remove a consumer, only add a join step. The evidence directories
are append-only historical records whose value is that they are frozen at the
revision they were captured at — folding them into a mutable generated file would
destroy exactly the property that makes them evidence. The real duplication
problem in this repository was never `profiles/`: it was 1.2 GB of superseded
native binaries in git history (see `docs/LESSONS.md`).
