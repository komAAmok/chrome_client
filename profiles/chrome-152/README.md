# chrome_152 profile

Evidence for the `chrome_152` profile, which is active in the table. Everything
here is regenerated by the commands below; none of it was hand-written.

## Files

| File | What it is |
| --- | --- |
| `captures.json` | 4 independent Chrome 152 connections to `tls.peet.ws/api/all` |
| `validation.json` | wire gate result, produced by `tools/verify-wire-capture.py` |
| `source-evidence.json` | the 12 audited source files at the 152 release tags, produced by `tools/collect-profile-evidence.py` |
| `trust-anchor-ids.json` | the 28 trust anchor IDs the captures advertise, in wire order |

Reproduce both:

```sh
tools/verify-wire-capture.py --profile chrome_152 \
  --captures profiles/chrome-152/captures.json \
  --out profiles/chrome-152/validation.json

tools/collect-profile-evidence.py --version 152.0.7977.83 --version 152.0.7977.42 \
  --out profiles/chrome-152/source-evidence.json
```

## Wire gate

`wire_verified: true`. 4 connections from 4 distinct source ports.

Byte-identical on every connection: de-GREASEd cipher list, supported groups,
signature algorithms, HTTP/2 fingerprint, trust_anchors payload, User-Agent.
Different on every connection (4 distinct values each, 3 required): client
random, session id, extension order, GREASE values, key share, ECH payload.

The extension set differs by exactly `pre_shared_key (41)`, present only on the
3 connections that resumed a session. That is expected and is why
`verify-wire-capture.py` treats resumption extensions separately instead of
demanding an identical set.

## The trust_anchors payload: the set is profile data, the order is not

The extension body is a sequence of one-byte-length-prefixed IDs, written by
BoringSSL's `ext_trust_anchors_add_clienthello` inside a u16 list length. So the
value handed to `SSL_set1_requested_trust_anchors` is the inner sequence, two
bytes shorter than the payload the wire shows: 184 bytes here, 186 on the wire.

**Which IDs** is frozen profile data. The captures consistently advertise 28. The
compiled-in Chrome Root Store has 32, in both the 152 tag and this repository's
pinned tree, and the 28 are a strict subset missing `d6790902`, `d6790903`,
`d6790909`, `d679090e` (all 11129.9.x). Order differs too. The capture machine had
a PKI-metadata-component-updated root store, and that state is in no source tree,
so the set is stored as observed.

**Their order is deliberately not frozen.** `SSLContextConfig::trust_anchor_ids`
is an `absl::flat_hash_set`, and absl gives every table instance its own seed —
`raw_hash_set.h`: *"Per table hash salt. This gets mixed into H1 to randomize
iteration order per-table."* `SelectAllTrustAnchorIDs()` iterates that set, so the
order is a property of the table instance, not of the release. Chrome builds the
set once per browser process, which is why its four captures share one order,
and a restarted Chrome advertises a different one.

The Core reproduces the mechanism rather than the artifact: it inserts the 28 IDs
into the same container type and lets absl order them. Measured with
`tools/inspect-client-hello.py`:

| | distinct orders | distinct sets |
| --- | --- | --- |
| one Engine, 4 requests | 1 | 1 |
| four Engines, same process | 4 | 1 |

Constant within an Engine, different between Engines — an Engine plays the role
of a browser process. Freezing the observed order would instead make every
instance emit the same permutation, which real Chrome never does.

## Verifying that no other profile moved

`tools/inspect-client-hello.py` reads the ClientHello back off a local socket, so
the claim is checked against the wire rather than the table. Sampling matters:
BoringSSL's RFC 7685 padding is length-dependent and the ECH GREASE payload
changes length between connections, so `padding` comes and goes for the same
profile and one sample per profile reads that as a change. With `--repeat 4`,
eleven profiles spanning 99 to 151 were captured before and after this change:
stable and varying extension sets identical for all eleven, and no pre-152
profile sends `trust_anchors`. That holds by construction — an empty span leaves
`trust_anchor_ids` empty, so `ShouldAdvertiseTrustAnchorIDs()` returns false.

## What differs from chrome_151

Three things, all provable from source:

**1. User-Agent version.** `151.0.0.0` → `152.0.0.0`, every other token
identical. `core/source/minicronet.cc` already emits `<major>.0.0.0` for any
major above 104, so no code change is needed.

**2. One new TLS extension: `0xca34` / 51764 = `TLSEXT_TYPE_trust_anchors`.**
JA3's cipher and curve segments are identical; JA4 goes from
`t13d1516h2_8daaf6152771_806a8c22fdea` to
`t13d1517h2_8daaf6152771_cb7bf5808d99` — the `1516` → `1517` is the extension
count, and the cipher hash `8daaf6152771` is unchanged. The Akamai HTTP/2
fingerprint is byte-identical, including the 15,663,105 window increment.

This is a real version-level change, not a component-update artifact:

| | Chrome 151 | Chrome 152 |
| --- | --- | --- |
| `kTLSTrustAnchorIDs` | `FEATURE_DISABLED_BY_DEFAULT` | `FEATURE_ENABLED_BY_DEFAULT` |
| `kNonMtcTrustAnchorIDs` | does not exist | `FEATURE_ENABLED_BY_DEFAULT` |
| selection | `SelectTrustAnchorIDs()`, only the intersection with server-advertised IDs | `SelectAllTrustAnchorIDs()`, all trusted anchors unconditionally |

So a Chrome 151 never sends the extension no matter how current its components
are: the flag is compiled off.

**3. GREASE in `signature_algorithms`.** The 152 captures carry a leading GREASE
value there that varies per connection (`0x5a5a`, `0xaaaa`, `0x8a8a`, `0xbaba`);
the 151 captures carry none. `kTlsGreaseSigalgs` is new in 152 and
`FEATURE_ENABLED_BY_DEFAULT` (`features.cc:965`), and
`ssl_client_socket_impl.cc:211` calls `SSL_CTX_set_grease_sigalgs_enabled`. This
needed no new machinery: `grease_signature_algorithms` is an existing profile
field, and the Core already resolves it per socket as
`has_profile ? profile_grease_signature_algorithms : feature default`, so 151
keeps its `false`.

For completeness, all 140 net feature defaults were diffed between the two tags.
Two flipped (`kTLSTrustAnchorIDs`, and `kNetworkQualityEstimatorIsPrivateHostCache`
which is not wire-visible), five are new and enabled, and seven were removed. Of
the removals only `kTcpSocketPoolLimitRandomizationForProxy` touches a profile
field, and the behaviour it gated is now unconditional
(`client_socket_pool_manager.cc` sets `g_allow_size_randomization_for_proxy = true`),
so `randomize_proxy_socket_pool_limit` stays true.

## Status

Activated. `core/source/minicronet/profile_table_generated.h` now carries
chrome_99--chrome_152, and `core/source/profile_ssl_config_service.cc` decodes the
stored sequence into `SSLContextConfig::trust_anchor_ids`.

The one judgement call, signed off before implementing: the 28-ID set is a
component-updated value frozen into a version-keyed table, so it is a snapshot of
the root store as it stood at capture time rather than a property of the release.
Refreshing it needs a new capture set.
