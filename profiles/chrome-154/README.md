# chrome_154 profile

Evidence for the `chrome_154` profile, which is active in the table. Everything
here is regenerated by the commands below; none of it was hand-written.

## Files

| File | What it is |
| --- | --- |
| `captures.json` | 6 independent Chrome 154 connections to `tls.peet.ws/api/all` |
| `validation.json` | wire gate result, produced by `tools/verify-wire-capture.py` |
| `source-evidence.json` | the 12 audited source files at the 154 release tags, produced by `tools/collect-profile-evidence.py` |
| `trust-anchor-ids.json` | the 28 trust anchor IDs the captures advertise, in wire order |

Reproduce both:

```sh
tools/verify-wire-capture.py --profile chrome_154 \
  --captures profiles/chrome-154/captures.json \
  --out profiles/chrome-154/validation.json

tools/collect-profile-evidence.py --version 154.0.8037.17 --version 154.0.8037.100 \
  --out profiles/chrome-154/source-evidence.json
```

Chrome's reduced User-Agent reports `154.0.0.0`, so the captures cannot be
attributed to a patch build. Instead all twelve audited files were compared
between the first (`154.0.8037.17`) and last (`154.0.8037.100`) 154 stable
releases: **eleven are byte-identical**. The twelfth,
`net/quic/quic_chromium_client_session.cc`, differs by two bytes and by **no
audited signal line** (every signal's count and first 32 line numbers are
identical), so the audited surface is branch-stable.

## Wire gate

`wire_verified: true`. 6 connections from 6 distinct source ports.

Byte-identical on every connection: de-GREASEd cipher list, supported groups,
signature algorithms, HTTP/2 fingerprint, trust_anchors payload, User-Agent.

Different on every connection (6 distinct values each, 3 required): client
random, session id, extension order, GREASE values, key share, ECH payload.

As in 152 and 153, the extension set differs by exactly `pre_shared_key (41)` on
the connections that resumed a session, which `verify-wire-capture.py` treats
separately.

## What differs from chrome_153: the version, not the fingerprint

Every stable value the wire gate checks is identical to the chrome_153 captures:
the de-GREASEd cipher, group and signature lists, the extension set, the HTTP/2
fingerprint (`1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`), and the
`trust_anchors` payload length (186 bytes of wire contents / 184 bytes of
encoded list, 28 IDs). The only wire difference is the User-Agent major,
`153.0.0.0` → `154.0.0.0`; `core/source/minicronet.cc` already emits
`<major>.0.0.0` for any major above 104, so no code change is needed. The profile
exists to pin the version so `chrome_154` impersonation reports the right UA
while reusing 153's wire parameters verbatim.

That reuse is not assumed: `tools/build-profile-entry.py` re-derives the
cipher/group/signature/extension values from these captures and **fails** if they
disagree with the inherited template before it writes an entry.

The trust_anchors payload carries the **same 28-ID set** as 153 in a **different
order**. That is expected and not profile-relevant: the order is a property of the
process's `absl::flat_hash_set` instance (see `profiles/chrome-152/README.md` for
the mechanism), so the 154 entry stores its own observed order and the Core still
inserts the set and lets absl order it. `tools/inspect-client-hello.py`
demonstrates the Core reproduces per-instance ordering rather than a frozen
permutation.

## Source-level support for "nothing moved"

`net/base/features.cc` at 154.0.8037.100 keeps every network feature the table
reads at its 153 value: `kAlpsForHttp2` (line 32) `FEATURE_ENABLED_BY_DEFAULT`,
`kTryQuicByDefault` (887) `FEATURE_ENABLED_BY_DEFAULT`, `kTLSTrustAnchorIDs`
(732) and `kNonMtcTrustAnchorIDs` (734) enabled, `kTlsGreaseSigalgs` (1022)
enabled, `kEnableTLS13EarlyData` (182) disabled. `net/socket/spdy_session.cc` --
the HTTP/2 stack the table configures -- is byte-identical between 153.0.8010.37
and 154.0.8037.100 (sha256
`666cf33958bc3ae1364dc0c71291d13e152422b85ad9b15d138c6094985c15be`).

`kAvoidH2Reprioritization` still exists at 154 (`features.cc:37`,
`FEATURE_DISABLED_BY_DEFAULT`) and was removed upstream in 155; the profile-owned
`avoid_h2_reprioritization` session parameter therefore keeps reading a `false`
default on every profile either way.
