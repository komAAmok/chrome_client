# chrome_157 profile

Evidence for the `chrome_157` profile, which is active in the table. Everything
here is regenerated by the commands below; none of it was hand-written.

## Files

| File | What it is |
| --- | --- |
| `captures.json` | 5 independent Chrome 157 connections to `tls.peet.ws/api/all`, all full handshakes |
| `validation.json` | wire gate result, produced by `tools/verify-wire-capture.py` |
| `source-evidence.json` | the 12 audited source files at `157.0.8103.39`, produced by `tools/collect-profile-evidence.py` |
| `trust-anchor-ids.json` | the 28 trust anchor IDs the captures advertise, in wire order |

```sh
tools/verify-wire-capture.py --profile chrome_157 \
  --captures profiles/chrome-157/captures.json \
  --out profiles/chrome-157/validation.json

tools/collect-profile-evidence.py --version 157.0.8103.39 \
  --out profiles/chrome-157/source-evidence.json
```

## The audited tag and the compiled tag are different

This profile is audited against `157.0.8103.39`, but the Core ships a library built
from `156.0.8078.31` (`58bcc148f76b`). That split is deliberate: moving the
compile baseline means rebuilding eight platform artifacts and re-adapting the
thirteen Chromium patches, which is a separate change with its own risk.

It does not change the wire. The whole point of auditing twelve source files is
to prove that the values the table stores have not moved, and for 156 all twelve
are byte-identical between `156.0.8078.31` and `156.0.8078.80` — so a Core
built from the former emits what the latter was captured sending.

`source-evidence.json` records both revisions (`chromium_commit` and
`compiled_core_chromium_commit`) so the split is machine-readable rather than
buried in prose.

## Wire gate

`wire_verified: true`. 5 connections from 5 distinct source ports.

Byte-identical on every connection: de-GREASEd cipher list, supported groups,
signature algorithms, HTTP/2 fingerprint, trust_anchors payload, User-Agent.

Different on every connection (5 distinct values each, 3 required): client
random, session id, extension order, GREASE values, key share, ECH payload.

All five connections are full handshakes: none carries `pre_shared_key (41)`,
so this capture needs no resumption handling and no edit of any kind.

## What differs from chrome_156: the version, not the fingerprint

Every stable value the wire gate checks is identical to the chrome_156 capture:
the de-GREASEd cipher, group and signature lists, the extension set (18 names),
the HTTP/2 fingerprint (`1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p`),
and the `trust_anchors` payload (186 bytes of wire contents, 28 IDs). The only
wire difference is the User-Agent major.

`tools/build-profile-entry.py` re-derives the cipher/group/signature/extension
values from these captures and **fails** if they disagree with the inherited
template, so the reuse above is checked, not assumed.

## Not asserted: branch stability across patch releases

Only one build of this branch was captured and audited, so
`patch_release_comparison.identical_across_patch_releases` is `null`. Claiming a
result that was never measured is worse than recording that it is unknown.
