# 三库并发对比：chrome_client / curl_cffi / wreq（低变量版）

一次性测量，不是发布门禁。目的是把「本项目同步/异步的并发能力在同价位 Python
客户端里处于什么位置」变成数字。**本文取代同名的早期版本**——那一版的服务器本身
是瓶颈，结论被推翻了，更正过程写在最后。

测量日期：本机、空闲（无后台构建），8 核，Python 3.12.3。

## 被对比的版本

| 库 | 版本 |
| --- | --- |
| chrome_client | 0.2.11，ABI 11，本地构建 |
| curl_cffi | 0.17.0 |
| wreq | pip 当前版（只有异步：`get()` 返回 Coroutine） |

## 先把变量压到最小

这一版的改动全部是为了让差异只剩「客户端实现」：

| 变量 | 怎么固定 |
| --- | --- |
| 服务器容量 | 纯 asyncio HTTP/1.1 keep-alive 服务器，用**原始 socket 客户端**实测 **1.8–2.2 万 rps**。早期版本用的 `ThreadingHTTPServer` 只有 **6.3k rps**，低于 wreq 的实测值——**那个服务器在测自己**。 |
| 负载 | 恰好 1024 字节，`Content-Length`，无分块、无 gzip。 |
| 路径 | 回环 127.0.0.1，RTT≈0。差距只来自调度与复制。 |
| 预热 | 计时前先发一次请求，连接建立不算在内。 |
| URL | 每请求一个不同路径。Chromium 对同一 cache key 的事务会串行化，共用 URL 测的是那个。 |
| 并发语义 | **两侧一致**：异步用 `asyncio.Semaphore(conc)`，同步用 `ThreadPoolExecutor(max_workers=conc)`。任何一侧都不会拿到更多的在飞请求。 |
| 连接数 | 不作为变量：不额外设上限也不放开，各库用自己默认值。 |
| 计时 | `perf_counter` 包住整批，**5 轮独立运行**取中位，同时报 min/max/spread。 |
| 进程 | **每个库独立进程**。同一解释器里先跑 chrome_client 再跑 curl_cffi.async，后者从 3108 掉到 19 rps。 |
| 服务器生命周期 | 每一轮新建，避免上一个库的 keep-alive 连接进入下一轮。 |

## 结果（400 请求/轮，5 轮取中位）

### chrome_client

| 并发 | sync | async |
| --- | --- | --- |
| 4 | 2916.7 | 2483.7 |
| 8 | **3367.4** | 2712.5 |
| 16 | 3167.9 | 2580.4 |
| 32 | 2912.2 | 2779.8 |
| 64 | 2640.7 | 2739.2 |

spread 全程 1.05–1.55x。

### curl_cffi

| 并发 | sync | async |
| --- | --- | --- |
| 4 | 1003.6 | 3901.6 |
| 8 | 938.6 | 4522.7 |
| 16 | 985.3 | **4681.7** |
| 32 | 996.0 | 4498.2 |
| 64 | 943.5 | 4640.0 |

spread 1.04–1.31x。

### wreq（只有异步）

| 并发 | async |
| --- | --- |
| 4 | 11949.1 |
| 8 | 13063.5 |
| 16 | 14982.4 |
| 32 | **16259.8** |
| 64 | 15678.8 |

## 结论

**1. 三个库的曲线现在都是平的**，没有任何一个随并发上升而崩掉。这本身就说明
上一版看到的「台阶」不是库的性质。

**2. 绝对吞吐的排序是稳定的**：wreq（12–16k）> curl_cffi.async（3.9–4.7k）
≈ chrome_client（2.5–3.4k）> curl_cffi.sync（0.94–1.0k）。

**3. chrome_client 的同步与异步几乎同速**（2.9–3.4k vs 2.5–2.8k），异步略低
但在 spread 之内。其他两个库的同步/异步差距很大（curl_cffi 差 4–5 倍），
因为 curl_cffi 的同步路径每请求都要过一遍线程。

**4. chrome_client 的并发峰值连接数恒为 6**（上一版数据；本版服务器不计数），
这是 Chromium 的每 origin TCP 上限——**是指纹保真的结果，不是缺陷**。它同时
解释了为什么 chrome_client 的曲线是平的：并发加到 64，也只有 6 条连接在工作，
其余在 socket pool 里排队。v11 的 `max_sockets_per_group` 可以显式放开，
默认 0 保持 6。

**5. 本机环回下 chrome_client 落后 wreq 约 5 倍**。这个差距**不能直接外推到真实
网络**：环回 RTT≈0，瓶颈全在每请求的调度与复制上；而在真实 RTT 下，每 origin
6 条连接会把 chrome_client 变成 `6 × 1/RTT` 的硬天花板（20 ms RTT 时约
300 req/s，见 `docs/ABI.md` v11 一节），wreq 可以开更多连接。也就是说**两种
极端下的排序可能相反**，谁在真实场景里赢取决于目标是单 origin 还是多 origin。
这里只报告测到的东西。

## 更正：上一版错在哪

上一版（`ThreadingHTTPServer`，200 请求/轮，3 轮）报告了 curl_cffi.async 在
c≥16 时掉到 **193 rps** 的台阶，并把它归因于 `curl_cffi/aio.py` 里
`_force_timeout` 每 100 ms 的 `socket_action`。

**归因是错的。** 用同一套 `ThreadingHTTPServer` 复现：

```
rps:  [3195.4, 3422.7, 3044.8, 396.7, 386.8]
wall: [0.125,  0.117,  0.131,  1.008, 1.034]   <- 秒
```

掉速的轮次 wall 恰好是 **1.008 / 1.034 s**，是 100 ms 的整数倍。我当时据此认定
是客户端的 100 ms tick。真正的原因是 **`ThreadingHTTPServer` 每连接一个线程，
6.3k rps 就饱和**，而饱和后的调度把整批完成时间量化到了服务器线程切换的粒度上
——1 s 附近与 100 ms 的整数倍只是巧合地重合。换成容量 1.8–2.2 万的 asyncio
服务器后，**193 rps 台阶消失，wall 恢复到 0.10–0.13 s**。

这条错误的形状和本项目里记过的另外两次一致：**测量到了真实现象（wall=1.03 s），
但归因给了错误的组件**。判据应该是「先把被测系统之外的容量测出来」，而不是
「找一个看起来对得上的常数」。

## 这份数据不能用来做什么

- 不是 HTTPS/H2/H3：全部明文 HTTP/1.1。H2 多路复用会改变 chrome_client 的
  峰值连接数（`MAX_CONCURRENT_STREAMS` 默认 100），本版没测。
- 不跨并发值比较「并发能力」：三者并发模型不同（6 条连接排队 / 按需开连接）。
- 不是生产容量规划：单机、回环、单进程。
